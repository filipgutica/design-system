# Design decisions

Each entry records a choice this language made, the options it rejected, and why. Read it before you change a component, so a new project does not try a rejected option again. [Component specs](components.md) hold the values; this file holds the reasons.

| Units | Core | Type (`--text-*`), spacing (`--space-*`), and control and row heights (`--control-*`, `--row`) are rem, as are the page literals that size text, padding, gaps, and line heights. Hairlines, focus rings and their offsets, shadows, fixed icon and box sizes, layout widths, and radii stay px. Media query breakpoints stay px and are out of scope here. | All px: text and controls ignored the reader's browser font-size setting. | Shape follows role | Core | One corner for each height of thing, after Astryx's radius scale (`meta/astryx@7032abf`, `theme/tokens.stylex.ts`: inner 4, element 8, container 12). Rows, actions, and fields are all 8px: places and picked rows (`--radius-inline`), controls that act or set a value in place with every option shown on one line (`--radius-control`: buttons, quiet actions, chips, and segmented controls), and typed fields, controls whose label wraps, and one-line controls that are not actions (`--radius-field`). A field's `--color-field-edge` border, not its shape, tells it from an action, whose border is transparent. Containers are 12px (`--radius-panel`); rows 4px inside one, such as menu rows, take 12 − 4 = 8px, the row corner. Small marks inside text or a row (checkboxes, keyboard keys, and mentions) are 4px (`--radius-mark`). Small state marks are pills (`--radius-pill`). A pill never holds text that can wrap, and nested rectangles are concentric. The owner chose this scale (option B) on 2026-11-22 from rendered comparisons on the board, after finding the board busy and its mixed corners clashing. The token names predate the rule: they say inline, control, and field, where the uses are rows, actions, and typed fields. The names stay, because a rename breaks every page that uses them. | The previous scale (6px rows, 10px actions and fields, 16px containers, 6px checkboxes and keys; option A): a 6px tab beside a 10px button and field clashed on the board, and 16px containers needed a 12px corner for rows inside them. The same structure at 10px and 14px (option C): on 28px controls and 24px chips, 10px reads as nearly a pill, the action shape the owner rejected; chips would have needed 28px or a 4px corner. Pill actions (`--radius-control` at 999px), the shape until 2026-11-22: the owner found pill buttons ugly. One radius for every role: small state marks lose the pill that sets them apart, and rows and containers lose the corners that tell a place from a holder. A list of components for each token with no reason: a new component had no rule to pick from. | rendered corners by role: `tests/catalogue/catalogue.spec.ts` "each component renders the corner radius of its role, and no other part has one", "the DESIGN.md shape table names each role token with its value"; slider track and thumb, and select picker: `tests/design-foundations.test.mjs` "the slider track, slider thumb, and select picker take their role’s corners"; no literal radius: `tests/design-foundations.test.mjs` "no page or the report stylesheet writes a literal corner radius" |

| Themes | Core | A theme sets only its inputs: a hue for light and for dark, and optionally its two fonts, its base radius (`--radius-base`), its neutrals (page, surfaces, hover, edges, and text, as a whole set for both modes), and, for a theme imported at runtime through the mapper, any of its 11 syntax colours (`--color-syntax-*`); theme files do not take syntax colours. Spacing, states, and status colours stay core. The base radius scales every corner but the pill and the circle together, as Radix Themes and shadcn do: rows, actions, and fields take it, small marks half of it, and containers one and a half times it (owner decision, 2026-11-24), so actions keep the field and row corner in every theme. Neutrals are an input so an open palette keeps its own surfaces: Catppuccin and GitHub's Primer ship as themes, each mapped by its palette's own roles and unaltered. Where a hue cannot carry the text on a selected fill at 4.5:1, the build takes the first of the theme's text colour, black, and white that can, as the token roles say. Every theme passes the contrast guards in both modes. Theme files use the W3C Design Tokens format (2025.10) and ship beside the CSS, so design-token tools can read and write them: one file per theme, with a `light` and a `dark` group of sRGB colour tokens. Tools read the two groups as separate tokens (`light.color-bg`, `dark.color-bg`), not as one token with two modes; the Design Tokens Resolver module expresses modes, and it can replace the groups once tools support it. Graphite Indigo is the default. The family sites' own hues ship as themes named for their colour, so a site can load its theme file in place of an inline hue pair: Lagoon (annoterm), Copper (devps), Iris (filip-stack), Lapis (Workbench), and Fern (wtree). Each theme's note names its site. Where a site's light hue falls just short of 4.5:1 as selected-row text, its theme takes the smallest OKLCH lightness step that passes and keeps the hue and chroma, so the selection keeps the hue; the site can adopt the theme's value. A third-party palette is never altered. The theme mapper (`./theme-mapper`, experimental) turns a VS Code colour theme into these inputs for its one mode by selection: each input takes the first of its keys whose colour passes that input's contrast gate, and no colour is changed. What still fails is reported, as a `theme` problem in the theme's colours or a `core` problem in a core link, status, or syntax colour on its fills. Command text and prompts follow the theme’s code text and accent, so their failures belong to the theme’s text and focus checks. The checks are data: every ink on every fill the catalogue draws, hover and pressed states included, so a state axe never renders is still measured. The mapper keeps an imported theme's syntax colours too, from its `tokenColors`: each role takes the rule nearest its scope family. A role the theme leaves out takes its core colour; keyword, string, number, and comment have core colours, and the other 7 follow one of them or the code text. The owner chose this on 2026-11-14 to support open themes as their authors made them: the person who installs a theme owns its contrast, so a failing syntax colour is reported as a `theme` problem, never blocked or replaced. Most imports report one: comments in 5 of 8 popular themes measure 2.4–3.7:1 on their own background. The checks stay at 4.5:1, the WCAG AA minimum for text of this size; 3:1 would clear only 2 of those 5. The build and the mapper share one engine for applying a theme, resolving it, and checking it. | The action shape as a theme input of its own (a pill or another corner): a pill brings back the action shape the owner rejected (see Shape follows role), and a corner of its own breaks the one-corner-per-height scale. Shape kept wholly core, as Primer, Carbon, Polaris, and Spectrum keep it: a theme could not round or square the whole scale. Linear and OpenAI themes: neither publishes an open palette, and their colours are brand identity. Pine and Mauve, the earlier invented themes: no product used them, and they read as unrelated to the family's sites. A grey-blue quiet theme (Slate): it sat beside the muted text and the info blue, so its selection read as metadata and its primary button looked disabled. Adjusting an imported colour until it passes: the result is no longer the theme, and nothing tells the reader it changed. Syntax colours kept core for imports: an import lost its author's code colours to stay clear of reports. A looser bar for syntax, such as 3:1: it is below AA for code text, and it clears few imports. | Per-theme contrast guards (`tests/design-foundations.test.mjs`), the base radius in a theme file (`tests/theme-files.test.mjs`), the catalogue's rendered recipes in every theme, the Themes page tests, and the theme mapper's tests (`tests/theme-mapper.test.mjs`, the React smoke test with the mode locked opposite the system's, and the catalogue test that every axe contrast failure is a reported problem) |

## Token names

The 2.0.0 token rename, in the earlier version series (see Versioning), renamed 56 short names to the names `@filipgutica/ui` already declared. No value changed. Each `tokens.css` line before the rename named its ui variable in a `ui:` comment, and that variable became the line's name. Where a comment named several, the first one did.

To update a page or stylesheet that still uses the old names, run `node scripts/rename-tokens.mjs <file>...`. It reads the table below. A test fails when an old name appears in `language/` outside this table.

Name a new token by these rules:

- Give it one name, with no alias.
- Use Tailwind 4's theme namespaces where one fits: `--color-<role>` for a colour, `--shadow-<role>` for a shadow, `--radius-<role>` for a radius, `--font-<role>` for a font family, and `--text-<step>` for a type size. Other families keep their prefix, such as `--space-*`, `--control-*`, `--weight-*`, and `--duration-*`.
- Name the role, not the value: `--color-error`, not `--color-red`.
- A component role that always has the same value as a general token is not a new token. The component uses the general token.
- Do not reuse an old name from this table.

## Known gaps

- Field focus is a 1px `--color-accent` edge with a faint 2px inset line. The edge reaches 3:1 for a focus indicator (WCAG 1.4.11): 6.61:1 against the light field fill and 6.26:1 against `--color-bg`, and 8.43:1 and 8.31:1 in dark. It is thinner than the 2px perimeter that the WCAG 2.2 AAA focus appearance criterion (2.4.13) asks for; the inset line, at 18% of the accent, does not reach 3:1 on its own.
- The off track of a switch or toggle (`color-mix(in srgb, var(--color-border) 90%, var(--color-well))`) has no contrast check. It falls below the 3:1 that WCAG 1.4.11 asks of a component's visible boundary in two shipped themes: Catppuccin light, 2.86:1 on `--color-surface`, and GitHub, 2.84:1 on `--color-surface` in light and on `--color-surface` and `--color-surface-raised` in dark. Both palettes are open and never altered, so a check would fail them. The knob's position still shows the state. A checkable off track needs a new recipe, such as unmixed `--color-border`, which the `edge` check already guards; that darkens the off track in every theme.
- In forced colors (high contrast), an invalid field shows the system edge, not the `--color-error` edge, focused or not; the error text carries the state. A visible high-contrast invalid edge needs an error colour validated against high-contrast fills.
